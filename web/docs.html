DiskRoom / documentation

Make room.
Keep the context.

A local CLI that plans cleanup around a free-space goal, with evidence you can inspect and a decision you control.

Release preparation: npm publication and native platform verification are not yet confirmed here. Installation commands below describe the intended published package. Source checkout instructions work before publication.

Getting started

Use Node.js 22 or newer and npm. Node is required to run DiskRoom even when your projects use Python, Java, or another language. There are no runtime npm dependencies, accounts, or background services. The release process requires verified prebuilt native safety support for each declared platform. Windows/macOS cleanup requires the native bridge; if it is unavailable, cleanup fails closed while scanning remains usable.

Install after publication

npm install --global diskroom
diskroom --version
diskroom

One-time use after publication: npx diskroom. Package download may require a network connection; a local scan does not.

Start with a scan

diskroom scan ./projects --target-free 5GB
diskroom scan ./projects --json

Scanning writes local audit records and changes no scanned artifacts. The output includes a run ID. Review and confirm a cleanup plan separately:

diskroom clean --scan <run-id>
diskroom history <run-id>

Run from a source checkout

node bin/diskroom.js --help
node examples/create-demo.mjs
node bin/diskroom.js scan <printed-demo-path> --target-free 1MB --json

The fixture script creates a new isolated temporary directory containing synthetic projects. It never cleans, downloads packages, or modifies existing projects. Replace the placeholder with the directory it prints. You can inspect the fixture before using it. Its package registry metadata is deliberately fabricated and uses example.invalid; do not install its dependencies. The small goal is normally already satisfied, so the expected cleanup plan is empty.

Build and test source cleanup

npm run build:native
npm run check
npm test
node native/smoke.mjs

The native build needs the platform C/C++ toolchain, Python for node-gyp, and Node development headers. It may download pinned build tooling and matching headers. Source scans need no native compilation. The repository’s docs/development.md explains offline builds and platform-specific requirements. A local build does not establish verified support for other systems.

A goal is total free space

5 GB means “finish with 5 GB free,” not “delete another 5 GB.” If 3 GB is already free, the plan needs an estimated 2 GB gain. If the goal is already met, the default plan selects nothing.

needed = max(0, target free − current free)

Decimal units use powers of 1,000: kB, MB, GB. Binary units use powers of 1,024: KiB, MiB, GiB. Bytes and positive decimal quantities are accepted, including 100kB and 2.5GiB. Reports store bytes.

DiskRoom works on meaningful units such as a whole dependency environment. It may reasonably exceed the goal; it does not remove random pieces of an installation to hit an exact byte count. After every operation, the engine checks actual free space before starting another.

Choose the scope explicitly

ScopeMeaning
cwdThe selected directory and its descendants; default is where you launched DiskRoom.
projectThe detected enclosing project, when one can be identified.
diskThe local volume containing the selected path. Review its actual root before scanning.
systemInteractive selection from detected local volumes, with separate goals and results. Unattended system selection is refused.

Global caches outside a project scope are not silently added. Links and mount boundaries do not expand an approved operation. A goal belongs to a particular volume; reclaiming another volume cannot satisfy it.

The audit workspace is separate

diskroom scan /path/to/projects --workspace /path/to/reports

This scans the projects folder and writes /path/to/reports/.diskroom. Without --workspace, the original working directory holds .diskroom. A wider scan does not silently move the audit to a disk root. Keep enough space for the compressed audit before cleaning.

Keyboard navigation

Use arrows or Tab to move, Space to toggle a candidate, Enter for a detail or action, and Escape to go back. In the report, / searches, f filters, s sorts, t changes tree/list view, a selects visible recommended candidates, n clears selection, i opens directory/project inventory, ? shows keys, and c opens plan review. Bulk selection does not include risky or protected items.

Ctrl+C stops further work and retains the audit that can be saved. It does not restore already deleted files. On the final screen the default is to decline cleanup; opening that screen is not consent.

Exit codes

0: completed, including no changes. 1: invalid input, runtime error, incomplete scan, or operation errors. 2: completed cleanup but target unmet. 130: user cancellation. A scan does not return 2 merely because the target needs future cleaning.

Detection is not permission to delete

Seven built-in detector families share one report, planner, confirmation flow, and audit format. A detected resource may be actionable, protected, or informational. The current implementation is deliberately conservative when its evidence is incomplete.

FamilyWhat appears in the reportExecution boundary
Node.jsProject node_modules, recognized generated outputs, npm/pnpm/Yarn/Bun cache locations.npm node_modules requires complete installed-package membership and matching manifest, npm lock, HTTPS registry URL, integrity, and version metadata, plus fresh content checks. Empty marker metadata is insufficient. pnpm/Yarn/Bun dependency layouts, probable build outputs, and shared manager stores are detection-only.
PythonRecognized virtual environments, bytecode and test caches, pip/uv stores.Evidenced venvs, strict bytecode caches with preserved adjacent source, and recognized pytest metadata can execute. Interpreter installations and shared stores are detection-only.
Java / JVMRecognized Maven/Gradle build outputs and cache locations.Only specific Maven/Gradle Java class directories where every class maps to preserved Java source can execute. Shared stores and mixed output are detection-only.
Runtime installationsRecognized version-manager installations.Detection and explanation only. An old version is not proof that no project or program needs it.
DockerRecognized storage; exact image, container, and volume inventory when a verified local daemon’s host storage is inside scope and on the target volume.Reviewed exact image removal and explicitly acknowledged stopped-container removal, without force or volume removal. Volumes, build cache, and virtual storage remain detection-only.
GitRepository storage, local refs/stash signals, and maintenance limits. Dirty/untracked/ignored classification remains unverified.Linux-only reviewed repacking through isolated metadata and pinned filesystem handles, retaining unreachable objects. macOS/Windows are detection-only. The detailed source documentation includes the exact detector rules, operation matrix, and current verification limits. A familiar folder name alone is not evidence that its contents can be safely discarded. A lockfile is useful evidence, but cannot guarantee future access to every dependency.

Safety, activity, and uncertainty

Recommended

Supported, sufficiently evidenced artifacts. Only enough are selected for the goal.

Review / risky

Not selected by default. Review evidence and any required acknowledgements.

Protected

Visible in reports, excluded from cleaning. Size never overrides protection.

Recoverability and current need have separate 0–100 heuristic scores, confidence levels, and reasons. These scores are not probabilities. Unknown is not zero.

DiskRoom uses available project, source-change, Git, and process signals. The default activity window is 30 days. The project you launch it from, explicit protected paths, its own program/runtime, and its audit are guarded. An archive marker can lower an age-based concern; it cannot override actual use or an explicit protection.

diskroom config protect add /path/to/important-project
diskroom config exclude add /path/to/skip
diskroom config archive add /path/to/old-project
diskroom config activity-days 60
diskroom config protect remove /path/to/important-project

Protection keeps a resource visible while disallowing cleanup. Exclusion removes it from the scan. Workspace configuration persists in .diskroom/config.json.

Linux observes accessible same-user /proc paths. macOS uses trusted system lsof for available cwd, executable mappings, and open files. Windows uses native-resolved system PowerShell/CIM for same-user executable and whole absolute argument paths, but cannot observe cwd or open handles. macOS/Windows coverage remains partial and prevents automatic recommendations. Missing helpers and query limits are visible in the report.

Process inspection is incomplete on some platforms and permission boundaries. DiskRoom reports missing evidence; it cannot guarantee that every open file or runtime dependency is discovered. It does not stop processes or elevate privileges to force a cleanup.

Scanning does not execute project scripts or install hooks. Paths are not interpreted by a shell. Before execution, fresh checks reject changed identities, unsupported operations, altered protection, and newly active resources. Links are not followed to widen deletion.

Concurrent malicious filesystem changes cannot be universally controlled by a portable JavaScript process. The engine refuses operations it cannot delimit; do not treat a cleanup tool as a sandbox for hostile users sharing write access to the same tree.

There is no telemetry, audit upload, or automatic remote backup verification. Your audit contains paths and operational metadata, so review and redact it before sharing publicly.

Git & Docker need extra context

Git

A clean working tree and an origin URL do not prove that a repository is backed up. Stashes, local branches, tags, ignored files, submodules, LFS objects, and worktrees can hold unique data. DiskRoom does not delete entire repositories or replace them with shallow clones in this release.

On Linux, the supported maintenance operation is conservative git repack -a -d -n --keep-unreachable, executed through isolated metadata and descriptor-pinned object directories. The subprocess does not load the original project configuration or hooks. It retains unreachable objects, refs, and reflogs and leaves the worktree untouched; it does not prune, expire reflogs, or update server-info. macOS/Windows maintenance is detection-only. Dirty/untracked/ignored classification remains unverified. Shared/worktree, shallow, partial-clone, alternate-object, in-progress, or unsupported layouts remain detection-only. Repacking requires at least the larger of 64 MiB or twice the object-store size in temporary free space, can save nothing, and is always a manual review choice.

Docker

DiskRoom does not run docker system prune or force-remove arbitrary Docker data. A stopped container can contain the only copy of its writable data. Volumes are detection-only and never preselected. Build cache shared across builds cannot be counted as exclusive disk savings.

Resource operations require a verified local socket or named pipe, an accessible host storage directory within the chosen scope, and the same target volume. Remote endpoints are refused before daemon contact. Selected images are removed by exact full ID with --no-prune and no force; referenced or multiply tagged images are protected. Selected created/exited containers require explicit acknowledgement that their writable layer will be lost, and are removed without force or volume removal. State is rechecked before execution. Build-cache pruning, volume removal, and Docker Desktop virtual-disk cleanup are unavailable. Shared-layer gains remain unknown; only fresh target-volume measurements determine whether the goal was met.

A local record of what happened

Runs are stored under <workspace>/.diskroom/runs/<run-id>. Durable run records use gzip-compressed JSON with schemaVersion: 1, run identity, and linked scan/clean IDs. Configuration remains ordinary JSON.

diskroom history
diskroom history <run-id> --json

The audit records the scope, target, candidates, rationale, plan, pre-operation intents, outcomes, and observed free-space measurements. Satisfied goals without deletion are recorded too. Help and history commands do not create fake scan or clean runs.

Each durable chunk is closed independently. A crash between an intent and a result leaves an unverified action, not an assumed success. If a required audit write fails, the engine does not start another destructive action.

Read compressed records directly

node --input-type=module -e "import{readFileSync}from'node:fs';import{gunzipSync}from'node:zlib';console.log(gunzipSync(readFileSync(process.argv[1])).toString())" "/path/to/summary.json.gz"

This reads one compressed record without executing project code. The schema and journal semantics are documented in docs/audit-format.md in the source repository. Treat all recorded free-space differences as observations; other processes may have changed the disk at the same time.

An audit is not a backup. Deletion is direct and may be irreversible. There is no general undo or automatic reinstall.

Restoring an environment

Each candidate includes restoration guidance and prerequisites. DiskRoom does not automatically run it. Review the instructions in the project’s own documentation first.

ArtifactTypical restorationRequirements
npm dependenciesnpm ci in the project.Matching manifest/lockfile, registry access, credentials where needed. Installation can run package scripts.
pnpm / Yarn / Bun (informational)Use the project’s matching manager and locked install workflow.These layouts are detection-only. General restoration guidance does not enable DiskRoom deletion.
Python environmentCreate a venv with the correct interpreter; reinstall from the project’s recorded dependency inputs.Interpreter, lock/requirements metadata, package sources, credentials, and any required native build tools.
Python bytecode / test cacheRun the application or tests again.Original source and dependencies. Rebuilding costs time.
JVM build outputRun the project’s documented Maven or Gradle build.Source, matching JDK/tooling, dependencies, credentials, and build inputs.
Unique logs, data, or archivesRestore from your own verified backup, if one exists.No general reconstruction is possible from filenames or an audit.

Registry availability can change. A manifest or lockfile records intent; it is not a permanent backup of package contents or local patches.

Platform verification

DiskRoom targets native Linux, macOS, and Windows terminals; Windows does not require WSL. Targeting a platform and testing it are different claims. The release manifest records verified status below.

PlatformRecorded release status
LinuxLinux x64: local Node 22/24 tests passed; release matrix pending
macOSNative verification pending
Windows / PowerShellNative verification pending

The repository includes intended CI for Node.js 22 and 24 across Linux x64/arm64, macOS Intel/Apple silicon, and Windows x64. Local Linux x64 tests passed on Node 22.23.3 and 24.19.0: 115 passed and four OS-specific skips per run. Local tarball installation and terminal checks passed. The cross-platform workflow has not run yet. A workflow definition is not itself a passing native test run. Optional managers and daemon-backed actions require their own verification; a successful scanner test does not prove every installed manager operation. Docker checks currently use a fake CLI and mocked responses, not a live daemon.

Filesystem allocation, hardlinks, mount discovery, permissions, and process visibility vary by platform. Unavailable measurements and incomplete discovery are surfaced explicitly. See the source verification notes for tested versions and remaining limits.

When something gets in the way

The goal is unmet, but large candidates remain.

Those resources may be protected, risky, shared, unsupported, or have unknown benefit. DiskRoom does not automatically escalate. Review the explanations, lower the goal, or choose a different explicit scope.

The scanner found no recommended candidates.

A newly modified or current project is protected. Other artifacts may lack restoration evidence. A scan can be useful even when its safe default plan is empty. Do not change timestamps or mark live resources as archived to force cleanup.

I have no room for the audit, or the workspace is read-only.

Choose a writable workspace with --workspace and start a new scan. DiskRoom will not move audit history silently or delete first to make room for evidence.

A candidate changed after the scan.

Its identity, activity, protection, or contents no longer match the approved evidence. The operation is skipped. Create a new scan and review a new plan; do not edit the saved report to force it through.

Process inspection is incomplete.

Permissions or operating-system facilities may prevent complete visibility. The report identifies uncertainty. A lack of detected processes does not prove that nothing uses a file.

The terminal says cleanup requires interaction.

Run diskroom clean --scan <run-id> from a real interactive terminal. Piped stdin, CI, and scripts do not provide the required confirmation. Scan and history can use --json instead.

A cleanup was interrupted, or a lock remains.

Inspect the run history and confirm no other DiskRoom process is active. Do not assume every planned deletion completed, and do not resume by editing journal files. See the repository’s recovery documentation before addressing a stale lock.

A manager or Docker is unavailable.

Read the detector’s issue entry. Unsupported managers and unreachable daemons are reported rather than replaced with broad filesystem deletion. Install or configure optional tools only if you intend to use them, then rescan.
